# TripGo - Сервис поездок (Лабораторная работа 1)

Бэкенд-сервис для управления поездками такси, разработанный в рамках совместной траектории Авито и НИУ ВШЭ НН.

## Требования
- Go 1.26
- Docker & Docker Desktop (для tripgoctl)
- Утилита `tripgoctl`

## Переменные окружения
Сервис конфигурируется исключительно через переменные окружения. Пример конфигурации находится в файле `.env.example`.
- `HTTP_ADDR` — адрес веб-сервера (по умолчанию `:8080`)
- `DATABASE_URL` — строка подключения к PostgreSQL
- `SHUTDOWN_TIMEOUT` — бюджет времени на Graceful Shutdown (по умолчанию `10s`)
- `DATABASE_MAX_CONNS` — максимальный размер пула БД (по умолчанию `10`)
- `DATABASE_MIN_CONNS` — минимальный размер пула БД (по умолчанию `2`)

## Быстрый запуск
1. Поднимите локальную инфраструктуру:
   ```bash
   tripgoctl cluster start
   tripgoctl environment start
   tripgoctl connect
   ```
2. Накатите миграции базы данных:
   ```bash
   make migrate
   ```
3. Запустите сервис:
   ```bash
   make run
   ```

## Архитектурные решения

### 1. Уровень изоляции транзакций
В менеджере транзакций `TxManager` по умолчанию выбран уровень изоляции **Read Committed**. 
* **Почему:** Этот уровень обеспечивает максимальную производительность базы данных и защищает от «грязного чтения». Логическая целостность данных (запрет двух активных поездок) полностью перенесена на уровень БД.

### 2. Запрет двух активных поездок у водителя
Бизнес-правило *"У одного водителя не может быть двух активных поездок"* реализовано через создание **Частичного Уникального Индекса (Partial Unique Index)** в PostgreSQL:
```sql
CREATE UNIQUE INDEX idx_trips_driver_active_unique ON trips(driver_id) WHERE status = 'active';
```
* **Почему:** Обычный `UNIQUE(driver_id)` запретил бы водителю совершать больше одной поездки за всю жизнь. Частичный индекс уникален только для строк со статусом `active`. Как только статус меняется на `completed`, индекс перестает отслеживать эту строку, позволяя водителю брать новые заказы. Ошибка базы данных `23505` успешно перехватывается репозиторием и превращается в доменную ошибку `ErrDriverBusy`.

### 3. Менеджер транзакций
Реализован контекстный `TxManager`. Он открывает транзакцию `pgx.Tx`, обогащает ей контекст (`context.WithValue`) и передает его дальше. Репозитории используют хелпер `GetQueryer(ctx)`, который прозрачно вытаскивает транзакцию из контекста. Если транзакции в контексте нет, запросы выполняются напрямую через пул `pgxpool.Pool`. Реализована поддержка вложенных вызовов (переиспользование текущей транзакции) и автоматический `ROLLBACK` при ошибках или паниках.

### 4. Защита от конкурентной гонки при завершении поездки
Метод `FinishTrip` защищен от гонки данных при помощи блокировки строки на чтение внутри транзакции:
```sql
SELECT status FROM trips WHERE id = $1 FOR UPDATE;
```
Если два параллельных запроса попытаются завершить одну и том же поездку, Postgres заблокирует второй запрос до окончания первой транзакции. Второй запрос прочитает уже измененный статус `completed` и вернет ошибку `409 Conflict`, предотвращая перезапись времени `finished_at`.
